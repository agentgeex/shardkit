## 一、需求分析

### 1.1 数据模型（来自 PROJECT_MANAGEMENT.md）

一个计划（plan）是一批 step（=`ao_task_execution`）的集合，step 之间通过三种关系构成**有向无环图（DAG）**：

| 关系字段 | 语义 | 图形映射 | 对应需求 |
|----------|------|----------|----------|
| `children[]` | 父 → 子的**结构包含**（父为容器，所有子完成后父才完成） | 实线箭头 父→子 | **1:N 扇出** |
| `parent_run_uuid` | 子 → 父 的反向指针（与 children 双写） | 同上（自愈补边） | N:1 |
| `prev_task` | **执行顺序依赖**（等前置 succeeded 才启动） | 虚线箭头 前置→当前 | **1:1 串行** |

四种典型拓扑（§3.5）：

```
串行 1:1      A ──▶ B ──▶ C
扇出 1:N      A ──┬──▶ B
                  ├──▶ C
                  └──▶ D
汇聚 N:1      B ──┐
              C ──┼──▶ E
              D ──┘
层级(计划套计划) PlanMain ─┬─▶ plan_execute(Plan_A) ─▶ Plan_A1
                          └─▶ plan_execute(Plan_B)
```

另有**定时串行**（§模式五）：各 step 只有 `scheduled_at`，无显式边，需按时间顺序串联展示。

### 1.2 功能需求（推断）

1. **拓扑可视化**：自动布局，正确表达串行/扇出/汇聚/层级/定时。
2. **状态着色**：每个 step 显示 `run_status`（pending / running / succeeded / failed / cancelled），实时反映执行情况。
3. **交互**：缩放、平移、拖拽、小地图、点击查看详情。
4. **层级下钻**：`plan_execute` 步可展开其子计划（计划套计划）。
5. **规模适配**：从 4 步的小计划到上百步的大计划都可读。

## 二、候选方案调研

### 2.1 渲染层（图形框架）

| 方案 | 许可 | Star | 与 React 栈契合 | 定位 | 结论 |
|------|------|------|----------------|------|------|
| **`@xyflow/react`（React Flow v12）** | MIT | 38.6K | ✅ 原生 React 组件 | 节点式编辑器/流程图事实标准 | ✅ **首选** |
| `reactflow`（同名 v11 旧包） | MIT | — | ⚠️ 已改名，勿用旧包 | 旧版 | ❌ 只用新包 `@xyflow/react` |
| `@antv/x6` | MIT | 6K+ | ⚠️ Vue 系为主，React 需适配 | 国产图编辑引擎，功能全 | 🟡 备选 |
| `cytoscape` + `react-cytoscapejs` | MIT | 10K+ | ⚠️ 命令式，React 封装薄 | 图论/大规模网络 | 🟡 大图备选 |
| `jsPlumb` | MIT/商业双许可 | — | ⚠️ | 连线库 | ❌ 许可复杂 |
| `mermaid` | MIT | 70K+ | ⚠️ 文本→SVG，非交互 | 静态图 | 🟡 只读兜底 |

> **选型依据**：React Flow 是 React 生态里"节点式 UI"的**事实标准**（Stripe、Typeform 等在用；MIT 许可；18.38M 周下载）。节点即普通 React 组件，**可直接复用项目现有的 Tailwind + shadcn 组件写节点卡**，与 ShardKit 技术栈零摩擦。v12 的 peer 依赖为 `react >=17`，**兼容项目现有 React 18**。

### 2.2 布局层（自动排版算法）

关系图光有渲染不够，节点坐标需算法计算。候选：

| 方案 | 算法 | 许可 | 特点 | 结论 |
|------|------|------|------|------|
| **`@dagrejs/dagre`** | Sugiyama（分层） | MIT | 轻量、专为 DAG、与 React Flow 官方示例标配 | ✅ **首选** |
| `elkjs` | ELK（Eclipse Layout Kernel） | EPL-2.0 | 更强（端口/正交布线/大图），但体积大、异步 | 🟡 大图升级路径 |
| `d3-hierarchy` / `d3-dag` | 树/分层 | ISC | 树好、DAG 需 `d3-dag` | 🟡 |

> **选型依据**：本需求是**分层 DAG**，dagre 的 Sugiyama 算法正是为此设计，体积小、同步、稳定。React Flow 官方示例即用 dagre。若未来 plan 规模激增（数百节点、需要正交布线），可平滑升级到 elkjs（React Flow 社区有成熟接法）。

### 2.3 候选栈对比一览

```
                        React 契合   DAG 布局   交互   许可    体积   推荐
@xyflow/react + dagre      ★★★       ★★★      ★★★   MIT    小    ✅ 首选
@antv/x6 + dagre           ★★        ★★★      ★★★   MIT    中    🟡
cytoscape + dagre          ★★        ★★★      ★★    MIT    中    🟡
elkjs(替 dagre)            ★★★       ★★★+     —     EPL    大    🟡升级
```

## 三、实现方案（已落地原型）

### 3.1 技术栈

```
@xyflow/react   ^12   —— 渲染 + 交互（缩放/平移/小地图/拖拽）
@dagrejs/dagre  ^3    —— 自动布局（分层 DAG）
React 18 + Tailwind + shadcn（复用项目现有节点样式）
```

安装：`npm install @xyflow/react @dagrejs/dagre`（原型已装）。

### 3.2 架构（三层，职责分离）

```
┌─────────────────────────────────────────────────────────┐
│ 数据层  mock.ts / 真实来源                                │
│   Plan { steps[] }  ← 结构化 严格对齐 PROJECT_MANAGEMENT §3.2 │
│   真实接入：ao_plan_query(plan_id) / ao_plan_list 的返回     │
└───────────────┬─────────────────────────────────────────┘
                │  planToFlow(plan)
┌───────────────▼─────────────────────────────────────────┐
│ 适配层  adapter.ts                                        │
│   ① 关系抽取：children/parent_run_uuid → 结构边(实线)      │
│                prev_task              → 时序边(虚线)      │
│   ② dagre 布局：rankdir=LR, nodesep/ranksep               │
│   ③ 输出 React Flow 的 nodes[] / edges[]                  │
└───────────────┬─────────────────────────────────────────┘
                │  nodes / edges
┌───────────────▼─────────────────────────────────────────┐
│ 视图层  plan-flow.tsx（页面） + step-node.tsx（自定义节点）│
│   <ReactFlow> + Background + Controls + MiniMap + Panel   │
│   StepNode：步骤名 / Agent / run_uuid / 状态徽标 / 层级标记 │
└─────────────────────────────────────────────────────────┘
```

### 3.3 关键设计点

#### ① 关系 → 边的映射（adapter.ts）

```ts
// 结构边：父→子（children 与 parent_run_uuid 双写只连一条，自愈补边）
(s.children ?? []).forEach((c) => add(s.run_uuid, c, "struct"));
if (s.parent_run_uuid) add(s.parent_run_uuid, s.run_uuid, "struct");
// 时序边：prev_task（虚线）
if (s.prev_task) add(s.prev_task, s.run_uuid, "dep");
```

- **实线** = 结构包含（父子），**虚线** = 时序依赖（prev_task）。两种语义一眼可分。
- 去重：children 与 parent_run_uuid 是同一关系的正反两个写法，只连一条边，避免重边。

#### ② 自动布局（dagre）

```ts
const g = new dagre.graphlib.Graph();
g.setGraph({ rankdir: "LR", nodesep: 40, ranksep: 90 }); // LR：左→右，贴合"流水线"观感
plan.steps.forEach((s) => g.setNode(s.run_uuid, { width: 240, height: 92 }));
rawEdges.forEach((e) => g.setEdge(e.source, e.target));
dagre.layout(g);
// 再按 dagre 结果写回 node.position
```

> `rankdir` 可切 `TB`（上→下）用于"瀑布流"观感；本原型用 `LR`。

#### ③ 自定义节点（step-node.tsx）

节点就是普通 React 组件，**直接复用项目 shadcn 风格**，含：
- 状态圆点（running 时 `animate-pulse`）+ 左侧色环（按 `run_status` 上色）
- 步骤名 / Agent / `run_uuid` / 定时时间
- `Layers` 图标标记"层级调度步"（`plan_execute` / `plan_generate_and_deploy`）

状态色表：`pending/draft`=灰 · `running`=蓝 · `succeeded`=绿 · `failed`=红 · `cancelled`=琥珀。

#### ④ 页面交互（plan-flow.tsx）

`fitView` 自适应 · `minZoom=0.2` · `<Controls>` 缩放工具 · `<MiniMap>` 大图导航 · `<Panel>` 计划元信息卡 + 图例。

### 3.4 覆盖的拓扑（原型内置 3 组示例）

| 预设 | 覆盖拓扑 | 步数 |
|------|----------|------|
| 书籍创作（层级计划） | 层级 + 扇出 + 汇聚 + 串行 | 8 |
| 项目创建（混合拓扑） | 扇出 + 汇聚 | 4 |
| 每日批处理（定时串行） | 定时串行 | 5 |


### 4.2 运行时（Playwright 无头浏览器实测）

```
$ node logs/_shot_flow.mjs
nodes= 8  edges= 8  errors= []      ← 书籍创作计划
nodes2= 5                            ← 定时串行计划
```

- **节点/边渲染正确**：8 步 plan 渲染 8 节点、8 条边，零控制台错误。
- **拓扑正确**：`部署主计划` 扇出 1→3 → 三条并行分支（各由虚线 prev_task 串联"部署→执行"）→ 汇聚 3→1 到 `合并成书`。
- **状态着色正确**：绿(完成)/蓝(执行中)/红(失败)/琥珀(取消)/灰(待执行) 与页头统计"共 8 步 · 完成 3 · 执行中 1 · 失败 1"一致。
- **无重叠/无孤立节点**，布局清爽。

## 五、接入真实数据（生产方案）

原型的数据层是 mock，**接入真实计划数据只需替换取值，视图层与适配层零改动**：

```
mock.ts 的 PLAN_* 常量
        ↓ 替换为
ao_plan_list(project_id)            → 计划列表（下拉/侧栏选择）
ao_plan_query(plan_id)              → 单计划元信息 + 所有 step 状态
   ↓
转换成 mock.ts 的 Plan 结构（字段名已 1:1 对齐 §3.2）
   ↓
planToFlow(plan) → <ReactFlow/>
```

字段对照（几乎零转换）：

| plan JSON（文档） | 本原型 PlanStep | 
|-------------------|-----------------|
| `run_uuid` | `run_uuid` |
| `task_id` / `agent_id` / `instruction` | 同名 |
| `children[]` / `parent_run_uuid` / `prev_task` | 同名 |
| `scheduled_at` / `timeout_seconds` | 同名 |
| —— | `status`（新增，接 `ao_task_execution.run_status`） |
| —— | `label`（新增，可由 task_id 映射任务目录名） |

> 建议 BFF 侧提供一个 `GET /plans/:id/graph` 或直接复用 `ao_plan_query`，前端只做"数据→图"的纯函数转换。

## 七、结论与建议

1. **首选栈：`@xyflow/react` + `@dagrejs/dagre`** — MIT 许可、React 生态事实标准、与现有 React 18 + Tailwind + shadcn 零冲突、体积小、官方示例即用 dagre。
2. **架构分三层**（数据 / 适配 / 视图），数据契约严格对齐 `PROJECT_MANAGEMENT.md §3.2`，接真实数据零改动。
3. **原型已可运行**（`/plan-flow`），覆盖串行/扇出/汇聚/层级/定时五类拓扑，状态着色 + 交互完备。
4. **升级路径清晰**：规模增大 → elkjs；交互增强 → 详情抽屉 + 实时刷新 + 层级下钻。
5. **备选**：若团队偏好国产技术栈，`@antv/x6` 为唯一有力备选；若只需静态只读图，`mermaid` 可作零依赖兜底。
6. **风险提示**：React Flow v12 是对外包的**当前主线**（勿用旧包名 `reactflow`）；dagre 为社区维护（`@dagrejs/dagre`），稳定性足够但若需长期企业级支持可评估 elkjs。
